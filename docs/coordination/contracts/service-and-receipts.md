# Service routing and receipt designs (UX09)

Authoritative schemas: `packages/shared/src/receiptDesign.ts`, and additive Order/event fields in `domain.ts`.

- Signed-in staff `GET /api/service-mode` and `PUT /api/service-mode` use `{mode: "counter" | "board"}`. A PUT is audited and broadcasts `service-mode.changed` to staff. Default is `board`, preserving existing operation.
- Every new order snapshots the current mode. Counter orders skip kitchen display, public pickup projection and automatic kitchen printing; they remain normal payable sales in POS history. Their existing fulfilment status is not interpreted as proof of physical handover. POS labels them Counter service. Switching modes affects future orders only; it never discards existing board tickets. Added tab rounds retain the order's mode. Idempotent retries retain the original mode.
- Order `templateVersion` snapshots the active immutable receipt/ticket design at creation (absent/zero means built-in). Each version contains separate `receipt` and `kitchen` designs. Issued orders keep using that version on reprint.
- New orders also snapshot `printBusiness` at creation; later business settings do not rewrite their printed identity. Legacy orders without a snapshot retain the previous current-business fallback.
- Owner `GET /api/admin/receipt-templates` returns `TemplateState` (current design and up to 30 previous version summaries). `PUT` accepts `SaveTemplateBody`. `POST .../restore` accepts `RestoreTemplateBody` and publishes the selected historical design as a new version. Stale `baseVersion` returns 409 without changing anything. Saves/restores are audited.
- Owner `POST /api/admin/receipt-templates/preview` accepts `PreviewTemplateBody`, returns printable `text/html` with fixed sample data. `POST .../test-print` accepts the same body and queues a labelled sample on the configured printer; 409 without a printer. It never allocates sale/receipt numbers or opens the drawer.
- Receipt number, item amounts, totals/tax and sale-status markers remain visible. REL09 adds owner-requested
  logo-only branding and independent visibility controls for optional details; see [receipt visibility](receipt-visibility.md).
  Custom text is escaped; variables are limited to `{{business}}`, `{{order}}`, `{{receipt}}`. No raw markup, scripts or ESC/POS commands are accepted.
- Pictures (logo, closing picture, lettering) are bounded, validated monochrome bitmaps, shared by browser SVG rendering and thermal raster printing: at most 576 dots wide (the full 80 mm paper), 400 high for a logo or closing picture and 240 for lettering. Conversion happens in the editor, locally, and requires no cloud. A picture wider than the printer's own paper is scaled down when it is printed, never cut off.
- **Personal receipts (UX12, 2026-10-10).** All additive and optional; a design saved before prints byte for byte as it did.
  - `TextStyle { size, bold, underline, inverse }` with `size` one of `small` (the printer's narrow font, a third more characters per line), `normal`, `tall`, `wide`, `large` (2x), `huge` (3x). Optional `nameStyle`, `titleStyle`, `subtitleStyle`, `footerStyle` on a design; absent means the look it always had. `numberSize` also takes `huge`.
  - `Lettering { text, font, size, bold, image }`: one line drawn by the editor in a font of that device and stored as a picture, so the paper shows what the editor showed on any printer. `nameArt` puts the visible business name in lettering; it is used only while its `text` still equals the business name the order was sold under, otherwise the visible name prints as text. REL09 can hide that separate name when branding is carried by the logo.
  - Messages (now up to 6) gain `size`, `underline`, `inverse`, `position` (`top` = above the items, absent or `bottom` = below the totals) and `art` (lettering). A message prints only when its `text` is not blank.
  - `closing`: a picture printed last, under the footer. `separator` also takes `double`, `dotted`, `stars`, `wave`.
  - ESC/POS used for the looks: `ESC M` (font), `GS !` (size), `ESC -` (underline), `GS B` (inverse), `GS v 0` (pictures, height as two bytes). Sent only when a line needs them.
  - The printable HTML page is a character grid as wide as the paper (48 or 32 characters), so the preview wraps where the paper does.
- **QR codes (UX13, 2026-10-10).** `DocumentDesign.codes` holds up to 3 `DesignCode`s: `kind` `wifi` (`ssid`, `password`, `security` WPA | WEP | nopass, `showPassword` to print the details as text too) or `link` (`value`: a web address or short text), each with `caption`, `size` (s, m, l = 4, 6, 8 printer dots per square) and `position` (top | bottom). The server computes the code (`packages/receipt/src/qr.ts`: byte mode, level M, up to 666 bytes) and prints it as a picture in whole dots, so no printer QR command is needed and the HTML preview shows the same squares. A code with nothing filled in is left out. The WiFi payload is `WIFI:T:<security>;S:<name>;P:<password>;;` with `\ ; , : "` escaped. A QR code holds a web address as data; it is never placed in the page as a link.
- Physical printer paper configuration is authoritative for thermal column width; editor paper width controls browser/preview printing. The editor makes this distinction visible. Printed output uses the same structured blocks in both renderers.

Storage: new append-only `receipt_templates(version, data, created_at, staff_id)` table. Each save/restore inserts a full design; update/delete/replace are blocked. Current version is the maximum version. Zero is permanent built-in fallback.
